# WalkWithMe guardian pairing

On the wearer's Android phone, start a session, then open **Settings → Show guardian QR code**. On the guardian's iPhone or Android, choose **Scan QR code** under **Join as guardian**. If the camera is unavailable, enter the displayed 10-character pairing code instead. No link needs to be copied or pasted. Pairing does not enable live sharing, acknowledge an alert or extend a check-in deadline.

Codes expire after five minutes or when the session expires, whichever comes first. Each code can be redeemed once. Generating a new code replaces the previous code for that session. Ending/deleting the session or revoking guardian access invalidates outstanding codes. Existing guardian access remains valid when generating or redeeming a code; revocation still removes all access for that guardian credential. The current app supports one saved session per phone.

Both phones must run the updated app against the same HTTPS service, and the backend must also be updated. The QR payload contains the WalkWithMe format/version, service origin and temporary pairing code, without owner/watch/guardian bearer credentials or geographic evidence. Scanning never follows a URL or changes the configured service. Camera processing stays local and images are not returned, recorded or uploaded. Camera permission is requested only when opening the scanner. Denied permission has a manual-code fallback. The scanner suspends the camera on lost focus and closes it after a successful scan or leaving the screen. A phone with active wearer recording cannot open the guardian scanner.

## Service behavior

`POST /api/sessions/:id/guardian-invite` requires owner authorization plus the current guardian token from the owner's saved session. It returns `code`, `expiresAt` and `serverNow`. The service verifies the token against the stored guardian hash. Invitation codes have 50 random bits, use letters/digits that exclude 0, 1, I and O, and are indexed by a SHA-256 digest. The existing bearer credential is held only in the temporary in-memory entry; session credentials remain hashed in persistent storage. Expired entries are swept by the server timer. A server restart invalidates unredeemed codes; create another code afterward.

`POST /api/guardian-invites/redeem` accepts `{ "code": "ABCDE-FGHJK" }` without an existing credential. Redemption atomically consumes the code, rechecks session lifecycle and current guardian access, and returns only the session ID and guardian credential. The app then verifies guardian scope through the existing session read before saving access. Redirects are disabled. A network failure after consumption may require a new code. Code requests are limited to 10 attempts per socket address per minute and 120 attempts per minute across the server; forwarded address headers are not trusted, so a tunnel may share the address limit across phones. At most 1,000 invitations are live at once, with one per session. Responses have `Cache-Control: no-store`; codes and credentials are not logged.

The Android scanner bundles its recognition dependency so scanning needs no first-use model download. This adds roughly 3–10 MB to the Android app. iPhone uses the native Vision camera scanner. QR generation uses a local Flutter renderer. Legacy link credentials remain compatible for existing builds and the browser, while the updated mobile interface uses QR/code pairing.

## Verification

`npm test` covers pairing authorization, lifecycle invalidation, expiry, replacement, atomic redemption, privacy and rate limits. Flutter tests cover payload validation, server-origin restrictions, guardian scope, invalid/expired responses, code rendering, access changes, camera denial, scan completion and camera lifecycle. The iOS integration suite uses pairing codes instead of pasted links. Android APK compilation checks scanner integration. Physical two-phone QR recognition and signed iPhone builds still need device verification.
